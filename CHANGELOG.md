# Changelog

One line per version, newest first. The version is printed by `python run.py --version`, written into every workflow trace and served by the API.

- 0.5.1: Week 7 failure catalogue (`docs/evaluation/failure-catalogue`): five failures recorded in the repository, each re-tested on 19 October 2026, with the live re-test evidence in `evidence/traces/failures/`; Week 7 progress report added. Documentation only.
- 0.5.0: Week 7 observability: the run log. Every check, workflow, agent run and search writes one JSON Lines file recording each model call (prompt version and fingerprint, sizes, tokens, timings, errors), each schema check, each item outcome, each search, each tool call, each planning decision and the run's outcome. No document text, quotation, prompt text or model answer is logged. `logs list|show|summary`; officer-only read permission; 90-day retention; `PROCURECHECK_LOGS=off` writes none. Traces now carry their run id.
- 0.4.6: Week 6 progress report added (`docs/weekly-reports/`). Documentation only.
- 0.4.5: Memory demonstration: `tests/evaluation/run_memory_demonstration.py` checks one submission three times (memory off, truthful memory, false memory) and compares everything the runs decide; live results and `docs/evaluation/memory-demonstration`. No change to the application's behaviour.
- 0.4.4: Memory data handling note added (`docs/architecture/`): what is stored, why, who can access it, retention and deletion, with the test that confirms each statement. Documentation only.
- 0.4.3: Weeks 2 to 4 progress reports rebuilt without the declaration, dedication and acknowledgement pages; member names moved to the title page and the division of work into the introduction. Documentation only.
- 0.4.2: Week 5 progress report added (`docs/weekly-reports/`). Documentation only.
- 0.4.1: Week 5 execution traces: `tests/evaluation/run_outage_recovery.py` captures a failure-and-recovery run against the real model; six recorded traces in `evidence/traces/`, set out in `docs/evaluation/workflow-execution-traces`. No change to the application's behaviour.
- 0.4.0: Week 6 persistent memory: case history. Each workflow run that reaches a report remembers the submission's item statuses (never its text) in a local SQLite store; the next run of the same submission ends with what changed since. Recalled outside the loop, so it reaches no decision, prompt or status. `--submission-id` and `--no-memory` on `workflow`; `memory list|show|forget|purge`; officer-only read, write and delete permissions; 180-day retention by default; synthetic resubmission sample.
- 0.3.1: Review fixes: the publish handler also checks sign-off rights; a declined or failed publication stops as not_published (exit 4) and is never retried; piped input never counts as sign-off; control characters are stripped from the sign-off prompt; backend details stay in the log; anonymous API calls are refused before uploads are read, and uploads are capped at 50 MB; the checklist is de-duplicated; a fault in the loop ends as tool_failed.
- 0.3.0: Human approval before a higher-impact action: the executor holds publish_completeness_report until a procurement officer signs off; simulated procurement record; `workflow --publish`; dropped steps are noted even when the run then stops.
- 0.2.0: Week 5 multi-step workflow by direct orchestration (`workflow` command, POST /workflow); create_review_ticket tool implemented to the Third Tool Specification; `--version` flag.
- 0.1.0: Weeks 1 to 4: completeness check with evidence adjudication, retrieval index and search, tools and model-driven tool calling. The version was not bumped per change before this log began.
